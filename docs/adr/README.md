# Architecture Decision Records

ADRs record accepted or proposed technical decisions with lasting architectural consequences. They do not activate product work and do not outrank verified source behavior, the project charter, current state, or active milestone.

## Required structure

Each new ADR should state:

- status: proposed, accepted, superseded, or rejected;
- context and the concrete problem;
- decision and owned boundary;
- alternatives considered;
- consequences, risks, migration, and rollback;
- related tests, evidence, and superseding ADRs.

The existing sequence includes the two-tier cognition boundary and extensive offline/provider/recording/run-store decisions. Read only the ADRs relevant to the active task. A historical provider ADR is not current authorization for network or paid execution.
